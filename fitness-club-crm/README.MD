# Fitness Club CRM

CRM система для фитнес клуба.

## Технологии

- Java 21
- Spring Boot
- PostgreSQL 18.6
- Docker
- JPA / Hibernate
- MapStruct
- Flyway
- Testcontainers
- JUnit
- Mockito
- MockMvc

## Управление клиентами
Реализован REST API для управления клиентами.

### Создание клиента

**POST `/api/v1/clients`**

Создание нового клиента.

#### Реализовано

- создание клиента через REST API;
- валидация входных данных с использованием Jakarta Bean Validation;
- преобразование DTO ↔ Entity с помощью MapStruct;
- сохранение клиента в PostgreSQL;
- миграции базы данных с помощью Flyway;
- проверка уникальности email на уровне приложения;
- ограничения `UNIQUE` для email и телефона на уровне базы данных;
- централизованная обработка ошибок через `GlobalExceptionHandler`;
- преобразование нарушений ограничений базы данных в понятные HTTP-ответы.

#### Обработка дублирования данных

Для защиты от создания клиентов с одинаковым email используются два уровня проверки:

1. `existsByEmail()` — предварительная проверка на уровне бизнес-логики.
2. `UNIQUE` constraint в PostgreSQL — окончательная гарантия целостности данных, в том числе при конкурентных запросах.

Нарушения известных ограничений преобразуются в соответствующие HTTP-ответы:

| Ограничение | HTTP-статус | Сообщение |
|---|---:|---|
| Дублирование email | `409 Conflict` | Client with email already exists |
| Дублирование телефона | `409 Conflict` | Client with phone already exists |
| Неизвестное ограничение БД | `500 Internal Server Error` | Database constraint violation |

### Обновление клиента

**PUT `/api/v1/clients/{id}`**

Полное обновление данных клиента.

#### Реализовано

- обновление клиента через REST API;
- валидация входных данных с использованием Jakarta Bean Validation;
- проверка существования клиента;
- проверка уникальности email с исключением текущего клиента;
- обновление существующей Entity через MapStruct;
- транзакционное обновление с использованием JPA dirty checking;
- обработка ситуации, когда клиент не найден;
- возврат `404 Not Found` для несуществующего клиента;
- возврат `409 Conflict` при попытке использовать email другого клиента.

#### Проверка уникальности email

При обновлении используется отдельная проверка:

```java
existsByEmailAndIdNot(String email, Long id);
```

Она позволяет текущему клиенту сохранить собственный email, но не позволяет присвоить ему email другого клиента.

Дополнительной гарантией целостности данных остаётся `UNIQUE` constraint в PostgreSQL.

## Валидация

Для проверки входных данных используется Jakarta Bean Validation.

В `ClientRequestDto` применяются ограничения:

- `@NotBlank`;
- `@Size`;
- `@Email`;
- `@Pattern`;
- `@Past`.

Валидация выполняется до передачи запроса в бизнес-логику.

## Обработка ошибок

Для централизованной обработки исключений используется `GlobalExceptionHandler`.

На текущем этапе обрабатываются, в частности:

- `ClientNotFoundException` → `404 Not Found`;
- `EmailAlreadyExistsException` → `409 Conflict`;
- `DataIntegrityViolationException` → обработка нарушений ограничений базы данных;
- неизвестные ошибки → `500 Internal Server Error`.

Формат ответа об ошибке:

```json
{
  "status": 404,
  "message": "Client with id '999' not found"
}
```
## База данных

Для управления структурой базы данных используется Flyway.
Текущие миграции:
- V1 — создание таблицы client;
- V2 — добавление birth_date;
- V3 — переименование database constraints для email и phone.

Для хранения данных используется PostgreSQL.

Для проверки стиля кода используется Checkstyle.

Конфигурация находится в:

```text

```

Проверяются, в частности:

- длина строк;
- именование методов;
- именование типов;
- wildcard imports;
- обязательность фигурных скобок.

## ADR-001 — PostgreSQL 18
Мы используем PostgreSQL 18.6, несмотря на предупреждение Flyway о том, что текущая версия Flyway официально не тестировалась с PostgreSQL 18. На текущем этапе миграции успешно валидируются и выполняются. Для учебного проекта решено сохранить PostgreSQL 18 и не снижать версию только из-за предупреждения.
