# Fitness Club CRM

CRM-система для управления фитнес-клубом. Проект разрабатывается как модульное backend-приложение с использованием современного Java-стека.

На текущем этапе реализованы модули управления клиентами и тарифами, а также доменная модель абонементов.

## Технологический стек

| Технология | Назначение |
|---|---|
| Java 21 | Основной язык разработки |
| Spring Boot 3 | Backend-приложение |
| Spring Web | REST API |
| Spring Data JPA | Работа с базой данных |
| Hibernate | ORM |
| PostgreSQL 18.6 | Реляционная база данных |
| Flyway | Миграции схемы БД |
| MapStruct | Преобразование DTO и Entity |
| Docker / Docker Compose | Контейнеризация и инфраструктура |
| Testcontainers | Интеграционное тестирование |

| Mockito | Мокирование зависимостей |
| MockMvc | Тестирование REST API |
| Checkstyle | Контроль стиля кода |

# Реализованный функционал

## 1. Управление клиентами

Реализован REST API для создания, получения, обновления и удаления клиентов.

### Создание клиента

`POST /api/v1/clients`

Создание нового клиента.

**Реализовано:**

- создание клиента через REST API;
- валидация входных данных с использованием Jakarta Bean Validation;
- преобразование DTO ↔ Entity с помощью MapStruct;
- сохранение клиента в PostgreSQL;
- миграции базы данных с помощью Flyway;
- проверка уникальности email на уровне приложения;
- ограничения UNIQUE для email и телефона на уровне базы данных;
- централизованная обработка ошибок через `GlobalExceptionHandler`.

### Получение списка клиентов

`GET /api/v1/clients`

Получение списка всех клиентов.

**Реализовано:**

- получение списка клиентов;
- преобразование Entity → DTO с помощью MapStruct;
- возврат списка в формате JSON.

### Получение клиента по ID

`GET /api/v1/clients/{id}`

Получение клиента по его идентификатору.

**Реализовано:**

- валидация идентификатора клиента;
- обработка ситуации, когда клиент не найден;
- возврат `404 Not Found` с информацией об ошибке.

### Обновление клиента

`PUT /api/v1/clients/{id}`

Полное обновление данных клиента.

**Реализовано:**

- валидация входных данных;
- проверка существования клиента;
- проверка уникальности email с исключением текущего клиента;
- обновление существующей Entity через MapStruct;
- транзакционное обновление с использованием JPA dirty checking;
- обработка ситуации, когда клиент не найден;
- возврат `409 Conflict` при попытке использовать email другого клиента.

Для проверки уникальности email при обновлении используется:

`existsByEmailAndIdNot(String email, Long id)`

Это позволяет клиенту сохранить собственный email, но не позволяет присвоить ему email другого клиента.

### Удаление клиента

`DELETE /api/v1/clients/{id}`

Удаление клиента по идентификатору.

**Реализовано:**

- удаление существующего клиента;
- обработка ситуации, когда клиент не найден;
- возврат `404 Not Found` для несуществующего клиента;
- возврат `204 No Content` при успешном удалении.

### Защита от дублирования данных

Для обеспечения уникальности email используются два уровня проверки:

1. `existsByEmail()` — предварительная проверка на уровне бизнес-логики.
2. UNIQUE constraint в PostgreSQL — гарантия целостности данных, в том числе при конкурентных запросах.

Нарушения известных ограничений преобразуются в понятные HTTP-ответы:

| Ограничение | HTTP-статус | Сообщение |
|---|---|---|
| Дублирование email | `409 Conflict` | Client with email already exists |
| Дублирование телефона | `409 Conflict` | Client with phone already exists |
| Неизвестное ограничение БД | `500 Internal Server Error` | Database constraint violation |

## 2. Управление тарифами (Tariff Management)

Реализован REST API для создания тарифов и получения информации о них.

### Создание тарифа

`POST /app/v1/tariffs`

Создание нового тарифа фитнес-клуба.

**Поддерживаемые типы тарифов:**

- `SELF_SERVICE` — самостоятельное посещение тренажёрного зала;
- `PERSONAL` — персональные занятия с тренером;
- `MINI_GROUP` — занятия в мини-группах;
- `GROUP` — групповые занятия.

**Реализовано:**

- создание тарифа через REST API;
- сохранение тарифов в PostgreSQL;
- преобразование DTO ↔ Entity с помощью MapStruct;
- валидация входных данных;
- проверка бизнес-правил между полями тарифа;
- генерация SHA-256 fingerprint для обнаружения дублирующихся тарифов;
- уникальность fingerprint на уровне базы данных;
- автоматическое создание новых тарифов в неактивном состоянии.

### Получение тарифа по ID

`GET /app/v1/tariffs/{id}`

Получение тарифа по его идентификатору.

**Реализовано:**

- получение тарифа через REST API;
- преобразование Entity → DTO;
- обработка ситуации, когда тариф не найден;
- возврат `404 Not Found`.

### Получение списка тарифов

`GET /app/v1/tariffs`

Получение списка всех созданных тарифов.

**Реализовано:**

- получение списка тарифов из PostgreSQL;
- преобразование Entity → DTO с помощью MapStruct;
- возврат списка тарифов в формате JSON.

### Валидация тарифов

Для проверки входных данных используется Jakarta Bean Validation и отдельный `TariffValidationService`.

**Базовая валидация:**

- `@NotBlank` — обязательное название тарифа;
- `@NotNull` — обязательные поля;
- `@Positive` — положительное количество посещений и длительность;
- `@Digits` — ограничение точности денежного значения.

**Дополнительные бизнес-правила:**

- для тарифов `SELF_SERVICE` обязательно указывается `AccessTime`;
- для остальных типов тарифов `AccessTime` не применяется;
- для безлимитного тарифа (`unlimited = true`) количество посещений не указывается;
- для тарифа с ограниченным количеством посещений обязательно задаётся `totalVisits`;
- длительность действия тарифа должна быть положительной.

Базовые ограничения проверяются через Bean Validation, взаимозависимости полей — через `TariffValidationService`.

### Обнаружение дублирующихся тарифов

Для обнаружения одинаковых тарифов используется SHA-256 fingerprint.

Fingerprint рассчитывается на основе совокупности характеристик тарифа:

- название;
- тип тарифа;
- категория клиента;
- признак безлимитности;
- количество посещений;
- длительность действия;
- временной режим посещения;
- стоимость.

Перед вычислением fingerprint нормализуются название и денежное значение.

Это позволяет обнаруживать одинаковые тарифы, даже если, например, название отличается регистром или лишними пробелами.

Для защиты от дублирования используются:

- предварительная проверка через `existsByFingerprint()`;
- уникальное ограничение `UNIQUE` на уровне PostgreSQL.

### Модель абонементов (Subscription)

Создана доменная модель абонемента, которая будет использоваться для оформления и учёта приобретённых клиентами тарифов.

**Предусмотренные характеристики:**

- клиент;
- название тарифа;
- тип абонемента;
- тренер;
- базовая и итоговая стоимость;
- признак безлимитности;
- общее и оставшееся количество посещений;
- даты начала и окончания действия;
- временной режим посещения;
- статус абонемента;
- признак бесплатной выдачи абонемента.

Для абонементов предусмотрены статусы:

- `NOT_ACTIVATED`;
- `ACTIVE`;
- `SUSPENDED`;
- `EXPIRED`;
- `CANCELLED`.

Модель хранит снимок характеристик тарифа на момент оформления абонемента. Это позволяет сохранять условия уже оформленных абонементов независимо от последующих изменений исходного тарифа.

**Текущий статус:** доменная модель, репозиторий и структура базы данных созданы. REST API и бизнес-логика управления абонементами находятся в планах дальнейшей разработки.

# Валидация и обработка ошибок

Для централизованной обработки исключений используется `GlobalExceptionHandler`.

На текущем этапе обрабатываются, в частности:

| Исключение | HTTP-статус |
|---|---|
| `ClientNotFoundException` | `404 Not Found` |
| `TariffNotFoundException` | `404 Not Found` |
| `EmailAlreadyExistsException` | `409 Conflict` |
| `DataIntegrityViolationException` | Обработка нарушений ограничений БД |
| Неизвестные ошибки | `500 Internal Server Error` |

Пример формата ответа:

```json
{
  "status": 404,
  "message": "Client with id '999' not found"
}
```

# База данных и миграции

Для управления структурой базы данных используется Flyway.

Hibernate не управляет созданием и изменением схемы БД (`ddl-auto: none`). Все изменения структуры выполняются через миграции Flyway.

Текущие миграции:

| Миграция | Назначение |
|---|---|
| V1 | Создание таблицы client |
| V2 | Добавление birth_date в client |
| V3 | Переименование ограничений email и phone |
| V4 | Создание таблицы subscription |
| V5 | Создание таблицы tariff |
| V6 | Добавление признака complimentary в subscription |
| V7 | Добавление fingerprint в tariff |
| V8 | Добавление snapshot-полей тарифа в subscription |

Для хранения данных используется PostgreSQL 18.6.

# Архитектурные решения (ADR)

## ADR-001 — PostgreSQL 18

В проекте используется PostgreSQL 18.6, несмотря на предупреждение Flyway о том, что текущая версия Flyway официально не тестировалась с PostgreSQL 18.

На текущем этапе миграции успешно валидируются и выполняются.

Для учебного проекта решено сохранить PostgreSQL 18 и не снижать версию только из-за предупреждения.
